# v0.2.0 execution governance

Three things claim to describe what v0.2.0 is: the epic prose in
[#573](https://github.com/MongLong0214/agent-operator-score/issues/573), the GitHub issues
themselves, and `governance/v0.2.0-execution-plan.json`. This document is about what happens when
they disagree, because they will.

## Why a manifest at all

The failure it exists to prevent already happened. #582 was closed on a documentation pull request.
In a list of issues that reads exactly like an implementation that landed: a reference, a merge, a
closed count. Everything downstream of #582 then looks unblocked, and an agent that trusts the
issue list starts building on a contract nobody wrote.

Prose cannot be checked. Labels rot — a status label outlives the work it described, a predecessor
merges and nobody relabels the successor, someone adds a dependency that quietly closes a loop. So
the plan is a file, the file has a schema, and a required check refuses to let the file, the schema
and GitHub drift apart.

An agent decides what to start by reading the manifest. Not the epic, not the newest comment, not
whichever body block looks most recent.

## The files

| Path | What it is |
| --- | --- |
| `governance/v0.2.0-execution-plan.json` | The plan. Thirty-two canonical issues, the dependency graph, phases, hot-file ownership, per-issue evidence contracts. |
| `schemas/aos-execution-plan.v1.schema.json` | The shape the plan must have. |
| `lib/execution-plan.mjs` | The checks. Offline; takes a GitHub snapshot as an argument. |
| `lib/github-state.mjs` | Reads live issues into snapshot shape, and parses completion records. |
| `scripts/verify-v020-execution-plan.mjs` | The command. |
| `fixtures/execution-plan/github-state.json` | A committed snapshot, so the suite runs with no network. |

## The commands

```bash
npm run verify:execution-plan        # static, offline, required in CI
npm run verify:execution-plan:live   # live GitHub read, JSON summary, release audit
```

Both run the same *plan and state* checks — the snapshot is an argument, so there is no second,
looser copy of them. Close evidence is the one thing they do not share: the static run reports it as
unestablished rather than passing it, for the reason below.

`--write-snapshot` refreshes the fixture from live state. It is a deliberate act that shows up as a
changed file in a diff, which is the point: the snapshot cannot drift silently.

The committed file is stamped `source: "snapshot"`, and the header is itself checked: schema,
repository, a strict ISO-8601 capture time, the integration branch the confirmations were made
against, and — crucially — that `source` matches how *this run* obtained the file. A hand-written
offline snapshot stamped `live` would otherwise read, in the evidence bundle, as an audit that had
just talked to GitHub. `--write-snapshot --branch something-else` is likewise not invisible
afterwards: the branch travels in the file and the plan declares which one ships.

None of that authenticates the file. A branch controlling both the plan and the snapshot can still
edit them into a mutually consistent fiction; what the header checks remove is the *cheap* version of
that -- a stale file, a file from another repository, one stamped with the wrong provenance or an
impossible date. The expensive version is why close evidence is not established offline at all, and
why the live job exists. The output also prints the snapshot's age.

The live summary carries counts, digests and issue numbers — never a title, a body, a path or a
token. It is written to be safe to paste into the release evidence bundle, because that is where it
goes.

## Scope

Canonical: **#553–#578, #582–#586, #588** — thirty-two issues, the epic #573 included.

Excluded: **#579, #580** (duplicates) and **#581** (an accidental admin issue). The verifier fails
if any of them is open in milestone 14, and fails if any appears in the plan.

## Status, and the two ways it goes wrong

`ready` means nothing is left to wait for. `blocked` means something is.

Both directions are checked, and the second is the one that rots:

- **ready with an unfinished predecessor** — work starts on a contract that does not exist yet.
- **stale blocked** — every predecessor passed and the label never moved, so available work looks
  unavailable and the release stalls on nothing.

`done` is the only status that means the GitHub issue should be closed.

## Phase-ready is not READY

An issue can be blocked and still have work that is safe to do. #556 has to know whether a platform
can enforce STRICT confinement at all before its predecessors land, and finding that out is a probe,
not an integration.

So a phase carries its own status *and* its own scope:

```json
{
  "id": "feasibility-proof",
  "status": "ready",
  "blocked_by": [],
  "allowed_outputs": ["safe-evidence-matrix", "platform-probe-record"],
  "code_integration_allowed": false
}
```

A phase that has begun -- `ready`, `in-progress` or `done` -- while its issue is blocked and claims
`code_integration_allowed` fails the check by name (`phase-scope-exceeded`). Checking only `ready`
left the permission reachable by moving the phase forward instead. An output outside the declared vocabulary fails too. The
distinction is load-bearing: phase-ready is permission to *learn something*, not permission to merge
the thing the block exists to withhold.

## Hot-file ownership

One surface, one primary owner. Two owners is how two branches rewrite the same schema and the
second merge silently wins.

```
construct/evidence/task   #582        result schema/aggregation  #559
operator events           #560        routing oracle             #558
reliance events           #583        suite/forms                #564
facet/uncertainty         #584        claim governance           #586
final contract freeze     #562        quickstart orchestration   #575
release channel           #569        execution governance       #588
```

## Close evidence

A closed issue has to say what closed it, in a fenced JSON block that names its schema, **posted by
someone with write access to the repository**:

````markdown
```json
{
  "schema": "aos-issue-completion.v1",
  "issue": 567,
  "final_sha": "…40 hex…",
  "pr": 601,
  "ci_run_ids": [12345, 12346],
  "verdict": "PASS",
  "evidence": { "raw_byte_digest_api": "sha256:…", "mutation": "load-bearing" }
}
```
````

The last such block on the issue wins. Prose that says "done" is not a record; a link to a PR is not
a record. Free text is read in four places -- this record, the V3 body marker, the title prefix, and the
pull request's closing reference -- and this is the only one where the *content* matters. It is read
for an exact typed object rather than for a judgement about what the author meant — an audit that has to interpret a
comment is an audit that can be talked out of its verdict.

`evidence` must carry the fields *that issue* declared in `required_evidence_fields` — and the plan
does not get to decide what those are. `EVIDENCE_CONTRACT` in `lib/execution-plan.mjs` pins the
required fields for all thirty-two issues, and the artifact bindings for the two that have them
(#588 and #570), outside the document being checked, because each of these was a one-line edit that passed everything:

```
close_evidence_required: false        the gate switched off from inside the plan
required_evidence_fields: ["x"]       non-empty, and asking for nothing
evidence_bindings: {}                 every digest confirmation vacuously true
owned_paths: ["README.md"]            "changed something it owns" true of a typo
phases: []                            #572's branch-deletion restriction removed
code_integration_allowed: true        the same restriction, kept but inverted
```

The last one is why `PHASED_ISSUES` pins each phase's *permission* and not only its name: the scope
rule fires when a phase is open on a blocked issue, and #572 is ready, so flipping that flag was
invisible.

`HOLD` keeps the issue open. So does a missing field.

### And the record is not believed

Forty hex characters, a positive integer and a non-empty array are things a fabricated record has
too. So the claims that can be checked go back to the repository — and go back as *one* claim, not
three. What "checked" covers is exact: the commit, the pull request, the workflow runs, the changed
files, and any evidence field the issue has a binding for. A field with no binding is checked for
presence and plausibility only, which is most of them.

Independently true facts are easy to come by: `dev` has hundreds of commits, the repository has
merged pull requests, and CI has succeeded thousands of times. Checking those three separately
confirmed nothing, because nothing tied them to each other. What is hard to fabricate is a pull
request whose merge produced *this* commit, closing *this* issue, with runs that executed on a
commit belonging to it.

| Confirmation | What it asks |
| --- | --- |
| `commit_exists` | the repository has that commit |
| `commit_on_integration_branch` | and it is an ancestor of the branch that ships |
| `pr_merged` | the pull request was merged |
| `pr_targets_integration_branch` | into the branch that ships, not somewhere else |
| `pr_closes_issue` | and its body closes this issue |
| `pr_produced_the_commit` | **its merge is that commit** |
| `ci_runs_succeeded` | every named run concluded `success` |
| `ci_runs_ran_on_this_work` | **on a commit belonging to that pull request** |
| `pr_changed_owned_files` | **the pull request changed something this issue owns** |
| `evidence_digests_match` | **the digests in the record are the artifacts at that revision** |

The last two exist because the first eight were still satisfiable without doing any work. A writer
could merge a documentation pull request whose body says `Closes #N`, name its merge commit and a
successful run on it, and produce eight true booleans having changed nothing. And the digests in the
record were compared to nothing at all — the first record filed for #588 quoted a manifest digest
that no longer matched the manifest, and the audit printed PASS.

So each issue declares `owned_paths`, and the closing pull request must have touched one of them;
and `evidence_bindings` maps an evidence field to a repository path, whose bytes are hashed **at the
recorded `final_sha`** and compared. At the recorded revision, not at the tip: evidence describes the
revision it was recorded against, and comparing it to HEAD would fail every time the file changed
for an unrelated reason.

All ten, individually. `{"verified": true}` on its own is a one-key forgery of the entire audit
and fails as `close-evidence-unverified`. A closed issue whose record has never been checked fails
as `close-evidence-unchecked` — a different failure from one that was checked and did not hold, and
neither is a pass.

The evidence values are read the same way: an empty array is not a digest, `false` is not a canary
result, and `0` is not a count.

**Who may attest.** Write access is asked of the repository — `admin`, `maintain` or `write` — not
inferred from `author_association`. A `COLLABORATOR` may hold the read or triage role, and that
account would otherwise have attested to completed work. "Could not establish" is not "has it".
If the permission lookup cannot be completed, the record fails as
`close-evidence-author-unchecked`, not `close-evidence-untrusted-author`: the audit has not
established the author lacks access, but it still has no attestation it can accept.

An outsider cannot overwrite a maintainer's record — the attempt is kept as `contested_by` rather
than dropped — and a maintainer's later correction does supersede an earlier pass. Comments are read
by following GitHub's `Link` header until there is no next page, so "the last record wins" does not
quietly become "the last record within some bound wins".

## What the checks are

Static, from the manifest alone:

```
schema valid                             canonical issue set is exactly 32
no duplicate / unknown / missing         no self dependency
no dependency cycle                      status and phase enums valid
exactly one priority, one area           release-critical implies close-evidence
hot-file owner collisions = 0            blocked_by ↔ blocks agree both ways
ready / in-progress / done have no       blocked is not stale, and neither
  unfinished predecessor                   is a blocked phase
phase output within vocabulary           phase-ready cannot integrate code
batches never run backwards              parallel peers are not dependencies
every release-critical issue except      all nine gates exist, and only those
  the epic is gated
the excluded list cannot be emptied      a done issue has no withheld phase
```

Every status that asserts work has begun or finished carries the same precondition. Constraining
only `ready` let an issue be moved to `in-progress` and then to `done` past its blockers — and
`done` predecessors are what unblock everything downstream, so it propagates.

Against GitHub, live or snapshot:

```
the snapshot says what it is             …for this repository, with a real date
open/closed state matches status         exactly one status: label, and it matches
exactly one priority:, and it matches    exactly one area:, and it matches
release: label present                   milestone == 14
title prefix matches priority (or EPIC)  V3 body marker present
a done issue is closed as `completed`     the three excluded issues are present,
                                           and not open in the milestone
the capture time is a real instant        (second 60 refused; see below)
```

Close evidence, for every closed issue — **live runs only**:

```
a typed aos-issue-completion.v1 record   from an author with write access
final SHA, PR, at least one CI run id    verdict PASS
every required_evidence_field present    all ten confirmations, individually
```

## Ready is not always ready in full

#572 may audit stale branches now and may not delete them until #578 has preserved the evidence. It
is issue-level `ready` with a blocked `final-deletion` phase, so the command says

```
restricted: #572 — only read-only-audit; withheld: final-deletion (waits on #578, #588)
```

rather than listing it under `ready now`. An issue with a blocked phase is never advertised as
plainly ready; printing "ready now: #572" was an invitation to do the destructive half.

## The cycle the DAG is checked against

`#564 → #584 → #585 → #586 → #562`, and **#564 does not wait on #562**. Adding that edge closes the
loop; the verifier reports it as `dependency-cycle` with the path spelled out.

The search runs only inside non-trivial strongly connected components, which is what makes it safe
on inputs that are not cyclic at all: a dense *acyclic* graph has zero cycles and exponentially many
simple paths, and enumerating from every node walked all of them before finding nothing. Two bounds
also apply — fifty reported cycles and a step budget — and hitting either is itself reported as
`cycle-search-truncated`, so a list that stopped early never reads as a complete one.

## Offline does not establish close evidence

The static check runs against a committed snapshot. That file is edited in the same pull request as
the plan, by whoever wrote the change, and nothing about it is authenticated: a contributor who
could not pass the live write-access check can still set every confirmation in it to `true`.

So the offline run does not *assert* that close evidence holds. It says so:

```
NOTE  #588: close evidence is only established by a live audit
INCOMPLETE  plan and GitHub state agree; close evidence for #588 is not established offline
            run `npm run verify:execution-plan:live` to establish it
```

Only `verify:execution-plan:live` establishes it. That runs as the `execution-plan-live` job on
pushes to `main` and on demand — not on pull requests, because a fork's token cannot read what it
needs and a required check that is skipped for forks is worse than one that runs where it can.

The offline verdict is the word `INCOMPLETE`, not a qualified `PASS`. `ok` and the exit status both
stay true, because they mean "nothing this run could check was wrong" and CI needs them; `verdict` is
the field that answers the other question, and it is the one to read. Every machine-readable signal
saying the same thing whether or not the evidence had been checked was the defect.

Reading a pass out of a file the author controls would be the same mistake as reading a verdict out
of a comment, which is the mistake this whole document exists to prevent. `{live: true}` is likewise
a caller's request, not a grant: the snapshot has to say `source: "live"` or the audit refuses.

Be clear about what that last check is worth. `source: "live"` is a field in the same editable file,
so it stops an accidental mislabel and not a deliberate one. Nothing a file says about itself can
authenticate it. What establishes evidence is a run that actually fetched from GitHub, which is why
the live audit exists as a CI job on `main` rather than only as a command someone could claim to
have run.

## What this does not do

It does not decide whether an implementation is correct. It decides whether the repository is
telling a consistent story about what has been implemented, and refuses to let an agent act on an
inconsistent one. Green here is not a measurement claim, and a closed issue is still not the same
thing as working software.

It also does not establish that the work was *good* — only that a pull request touching this issue's
files produced the recorded commit, that CI ran on it, and that any digest the issue has a binding
for describes that revision. A thorough change and a shallow one that touches the same file are indistinguishable here.
That judgement is a reviewer's, and nothing in this file replaces it.

## Operational limits of the v1 schema

The plan is bounded so that a malformed one is rejected rather than analysed: at most 64 issues, and
at most 64 entries in any of `blocked_by`, `blocks`, `allowed_parallel_with`, `owner_surfaces`,
`owned_paths`, `required_evidence_fields`, a phase's `blocked_by` or a gate's membership; at most 8
phases per issue, 32 outputs per phase and 16 gates.

These are v1 limits, not opinions about how large a release may be. This release uses 32 issues and
a semantic maximum of 31 references per issue, so the headroom is comfortable. A future release that
genuinely needs more bumps the schema version rather than removing the bound — an unbounded array is
how a canonical-sized plan carried a hundred thousand references and made the checks below it
unbounded work.

## What the capture time accepts

`captured_at` must be a strict ISO-8601 instant naming a day that exists, and **second 60 is
refused**. That is deliberately narrower than RFC 3339, which permits a leap second at the end of a
month in which one was actually inserted. Honouring that properly needs a table of announced leap
seconds, and a table in this file would go stale. Two weaker rules were tried and both accepted
instants that do not exist — `se === 60` unconditionally, and then checking only the UTC
minute-of-day, which made `2026-01-01T23:59:60Z` valid. The value is produced by `toISOString`, which
never emits 60, so refusing it costs nothing real and claims nothing false. The explicit check is
redundant defence: `Date.parse` refuses second 60 as well, which the mutation manifest established
by leaving the clause breakable with no test able to notice.
