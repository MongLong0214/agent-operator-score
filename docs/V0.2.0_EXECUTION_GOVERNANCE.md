# v0.2.0 execution governance

Three things claim to describe what v0.2.0 is: the epic prose in
[#573](https://github.com/MongLong0214/agent-operator-score/issues/573), the GitHub issues
themselves, and `governance/v0.2.0-execution-plan.json`. This document is about what happens when
they disagree, because they will.

## Why a manifest at all

The failure it exists to prevent already happened. #582 was closed on a documentation pull request.
In a list of issues that reads exactly like an implementation that landed: a reference, a merge, a
closed count. Everything downstream of #582 then looks unblocked, and an agent that trusts the
issue list starts building on a contract nobody wrote.

Prose cannot be checked. Labels rot — a status label outlives the work it described, a predecessor
merges and nobody relabels the successor, someone adds a dependency that quietly closes a loop. So
the plan is a file, the file has a schema, and a required check refuses to let the file, the schema
and GitHub drift apart.

An agent decides what to start by reading the manifest. Not the epic, not the newest comment, not
whichever body block looks most recent.

## The files

| Path | What it is |
| --- | --- |
| `governance/v0.2.0-execution-plan.json` | The plan. Thirty-two canonical issues, the dependency graph, phases, hot-file ownership, per-issue evidence contracts. |
| `schemas/aos-execution-plan.v1.schema.json` | The shape the plan must have. |
| `lib/execution-plan.mjs` | The checks. Offline; takes a GitHub snapshot as an argument. |
| `lib/github-state.mjs` | Reads live issues into snapshot shape, and parses completion records. |
| `scripts/verify-v020-execution-plan.mjs` | The command. |
| `fixtures/execution-plan/github-state.json` | A committed snapshot, so the suite runs with no network. |

## The commands

```bash
npm run verify:execution-plan        # static, offline, required in CI
npm run verify:execution-plan:live   # live GitHub read, JSON summary, release audit
```

Both run the *same* comparison. A live path with looser rules is how a release passes an audit the
suite would have failed, so there is only one set of checks and the snapshot is an argument to it.

`--write-snapshot` refreshes the fixture from live state. It is a deliberate act that shows up as a
changed file in a diff, which is the point: the snapshot cannot drift silently.

The committed file is stamped `source: "snapshot"`, and the header is itself checked: schema,
repository, a strict ISO-8601 capture time, the integration branch the confirmations were made
against, and — crucially — that `source` matches how *this run* obtained the file. A hand-written
offline snapshot stamped `live` would otherwise read, in the evidence bundle, as an audit that had
just talked to GitHub. `--write-snapshot --branch something-else` is likewise not invisible
afterwards: the branch travels in the file and the plan declares which one ships.

Without all of that, a branch controlling both the plan and its comparison authority could edit the
pair into a mutually consistent fiction and the check would agree with itself all the way to green.
The output also prints the snapshot's age.

The live summary carries counts, digests and issue numbers — never a title, a body, a path or a
token. It is written to be safe to paste into the release evidence bundle, because that is where it
goes.

## Scope

Canonical: **#553–#578, #582–#586, #588** — thirty-two issues, the epic #573 included.

Excluded: **#579, #580** (duplicates) and **#581** (an accidental admin issue). The verifier fails
if any of them is open in milestone 14, and fails if any appears in the plan.

## Status, and the two ways it goes wrong

`ready` means nothing is left to wait for. `blocked` means something is.

Both directions are checked, and the second is the one that rots:

- **ready with an unfinished predecessor** — work starts on a contract that does not exist yet.
- **stale blocked** — every predecessor passed and the label never moved, so available work looks
  unavailable and the release stalls on nothing.

`done` is the only status that means the GitHub issue should be closed.

## Phase-ready is not READY

An issue can be blocked and still have work that is safe to do. #556 has to know whether a platform
can enforce STRICT confinement at all before its predecessors land, and finding that out is a probe,
not an integration.

So a phase carries its own status *and* its own scope:

```json
{
  "id": "feasibility-proof",
  "status": "ready",
  "blocked_by": [],
  "allowed_outputs": ["safe-evidence-matrix", "platform-probe-record"],
  "code_integration_allowed": false
}
```

A phase that is open while its issue is blocked and claims `code_integration_allowed` fails the
check by name (`phase-scope-exceeded`). An output outside the declared vocabulary fails too. The
distinction is load-bearing: phase-ready is permission to *learn something*, not permission to merge
the thing the block exists to withhold.

second merge silently wins.

## Close evidence

A closed issue has to say what closed it, in a fenced JSON block that names its schema, **posted by
someone with write access to the repository**:

````markdown
```json
{
  "schema": "aos-issue-completion.v1",
  "issue": 567,
  "final_sha": "…40 hex…",
  "pr": 601,
  "ci_run_ids": [12345, 12346],
  "verdict": "PASS",
  "evidence": { "raw_byte_digest_api": "sha256:…", "mutation": "load-bearing" }
}
```
````

The last such block on the issue wins. Prose that says "done" is not a record; a link to a PR is not
a record. This is the only place the audit reads free text, and it reads it for an exact typed
object rather than for a judgement about what the author meant — an audit that has to interpret a
comment is an audit that can be talked out of its verdict.

`evidence` must carry the fields *that issue* declared in `required_evidence_fields`. A documentation
change can produce a reference, a merge and a closed count. It cannot produce the digests, the
canary and the mutation result the issue asked for by name.

`HOLD` keeps the issue open. So does a missing field.

### And the record is not believed

Forty hex characters, a positive integer and a non-empty array are things a fabricated record has
too. So every claim goes back to the repository — and goes back as *one* claim, not three.

Independently true facts are easy to come by: `dev` has hundreds of commits, the repository has
merged pull requests, and CI has succeeded thousands of times. Checking those three separately
confirmed nothing, because nothing tied them to each other. What is hard to fabricate is a pull
request whose merge produced *this* commit, closing *this* issue, with runs that executed on a
commit belonging to it.

| Confirmation | What it asks |
| --- | --- |
| `commit_exists` | the repository has that commit |
| `commit_on_integration_branch` | and it is an ancestor of the branch that ships |
| `pr_merged` | the pull request was merged |
| `pr_targets_integration_branch` | into the branch that ships, not somewhere else |
| `pr_closes_issue` | and its body closes this issue |
| `pr_produced_the_commit` | **its merge is that commit** |
| `ci_runs_succeeded` | every named run concluded `success` |
| `ci_runs_ran_on_this_work` | **on a commit belonging to that pull request** |

All eight, individually. `{"verified": true}` on its own is a one-key forgery of the entire audit
and fails as `close-evidence-unverified`. A closed issue whose record has never been checked fails
as `close-evidence-unchecked` — a different failure from one that was checked and did not hold, and
neither is a pass.

The evidence values are read the same way: an empty array is not a digest, `false` is not a canary
result, and `0` is not a count.

**Who may attest.** Write access is asked of the repository — `admin`, `maintain` or `write` — not
inferred from `author_association`. A `COLLABORATOR` may hold the read or triage role, and that
account would otherwise have attested to completed work. "Could not establish" is not "has it".

An outsider cannot overwrite a maintainer's record — the attempt is kept as `contested_by` rather
than dropped — and a maintainer's later correction does supersede an earlier pass. Comments are read
by following GitHub's `Link` header until there is no next page, so "the last record wins" does not
quietly become "the last record within some bound wins".

## What the checks are

Static, from the manifest alone:

```
schema valid                             canonical issue set is exactly 32
no duplicate / unknown / missing         no self dependency
no dependency cycle                      status and phase enums valid
exactly one priority, one area           release-critical implies close-evidence
hot-file owner collisions = 0            blocked_by ↔ blocks agree both ways
ready / in-progress / done have no       blocked is not stale, and neither
  unfinished predecessor                   is a blocked phase
phase output within vocabulary           phase-ready cannot integrate code
batches never run backwards              parallel peers are not dependencies
every release-critical issue is gated    all nine gates exist, and only those
the excluded list cannot be emptied      a done issue has no withheld phase
```

Every status that asserts work has begun or finished carries the same precondition. Constraining
only `ready` let an issue be moved to `in-progress` and then to `done` past its blockers — and
`done` predecessors are what unblock everything downstream, so it propagates.

Against GitHub, live or snapshot:

```
the snapshot says what it is             …for this repository, with a real date
open/closed state matches status         exactly one status: label, and it matches
exactly one priority:, and it matches    exactly one area:, and it matches
release: label present                   milestone == 14
title prefix matches priority (or EPIC)  V3 body marker present
a done issue is closed as `completed`     the three excluded issues are present,
                                           and not open in the milestone
```

Close evidence, for every closed issue:

```
a typed aos-issue-completion.v1 record   from an author with write access
final SHA, PR, at least one CI run id    verdict PASS
every required_evidence_field present    every claim confirmed by the repository
```

## Ready is not always ready in full

#572 may audit stale branches now and may not delete them until #578 has preserved the evidence. It
is issue-level `ready` with a blocked `final-deletion` phase, so the command says

```
restricted: #572 — only read-only-audit; withheld: final-deletion (waits on #578, #588)
```

rather than listing it under `ready now`. An issue with a blocked phase is never advertised as
plainly ready; printing "ready now: #572" was an invitation to do the destructive half.

## The cycle the DAG is checked against

`#564 → #584 → #585 → #586 → #562`, and **#564 does not wait on #562**. Adding that edge closes the
loop; the verifier reports it as `dependency-cycle` with the path spelled out.

## What this does not do

It does not decide whether an implementation is correct. It decides whether the repository is
telling a consistent story about what has been implemented, and refuses to let an agent act on an
inconsistent one. Green here is not a measurement claim, and a closed issue is still not the same
thing as working software.
